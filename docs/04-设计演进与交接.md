> 用户：“给到一份交接文档，你的设计我看起来不喜欢”

**交接结论**　v0.4 的界面设计未获 用户 认可，暂未确定新的视觉方向。保留原型供查看和复现，只把确认过的需求、职权边界和可验证的交互行为交给下一轮。暗色配色、等轴测建筑、总图构图、面板布局和首次导览的形式都是本轮设计选择，可重做。用户 没有指出具体不喜欢哪一处，不能从这句反馈推断原因。

## 1. 用户 已明确的产品要求

| 要求 | 接手时按什么理解 |
|---|---|
| 官制与经略分开 | **官制**是保留的现行规则与职权契约。**经略**是它的产品化迭代，独立持有对话、案卷和流程状态。下载后由经略自身提供配置和使用入口。 |
| 一个 API 就能开始 | 仅一个已配置且可用的模型 API，就能办完能力和授权范围内的普通任务。仅有一个受支持的本机 Agent 时也能单独使用。Codex、OpenCode 等可作为可选执行者，基础使用和周报触发由产品流程承载。 |
| 同一对话多模型、跨 Agent 接力 | 用户可为部门设主用、备用和全局默认，也可临时指定或接受基于实际能力的推荐。换部门时可自动换执行者，案号、授权和历史连续。每步显示实际执行者。强制独立复核时，单一身份停在待复核。 |
| 小小事直达，大事流转 | 大事体现内阁票拟与会签、三省分工和六部办理。有权审批的身份、批示版本、范围、退回原因要能查。需要朱批时由 用户 决定，门下负责复核及正式封驳，尚书在有效授权内派办。 |
| 中枢、衙门和完整王朝版图 | 中枢应能交办和处理待办。各官署有可辨识、可进入的实际场所，例如门下省有自己的衙门，进去能找到本署的案卷和动作。完整王朝版图展示业务进展。三者共享同一案卷；导航结构和场景画法可重新提案。 |
| 行省、府州、县与熟地 | 行省对应稳定业务类别，如工作、学习、视频制作。府与州同级，对应客户、项目或长期主题。县对应可交接或验收的节点。同一县可换人、重试或重开，沿用稳定案号。已有类别无法容纳持续业务时可开新省。 |
| 地块状态、县志和周报 | 办理中、灰地、领地和熟地应能看懂。未接壤由实际前置条件决定；办完以真实验收为准。验收后默认 7 天并入熟地，可改期限。版图保留摘要，县志可定位原案和获准原件，允许配置保存或跳转位置。每周五 16:00 汇总工作、优化、学习方法、创作等已记录成果，由共用流程判期、认领、去重和补报。 |
| 御史查漏与分权 | 御史巡按查漏纳管、错归类、流程或越权疑点。察院登记，大理寺独立核事实，属实按程序交内阁处置，正式封驳归门下，台院独立复验销案。各自有独立操作入口和证据；上报、核证和处置的权限分开。分类或开省建议由用户确认后落地。 |

设计语言方面，用户 明确要达到面向用户交付的水准，要求官府和衙门具象化，也曾提出希望更有科幻感或古典感。先用场景和操作让 用户 评审具体方向。界面按共用规则做文字减法，保留必要状态、错误原因与操作名称；同时评审用户操作成本、开发维护成本和 Agent 可操作性。 [需求 v0.3](./02-需求说明书.md) · 版图要求 · 共用规则 · 周报程序约定

## 2. 现在可以打开和复现什么

用 Chrome 或 Edge 打开本地 `原型-v0.4/index.html`。页面使用合成业务数据。交办页选择“启用演示 API”即可操作，无需密钥。测试首次使用时用新浏览器上下文，避免影响已有的演示草稿和状态。

| 从哪里进 | 可复现的行为 |
|---|---|
| [中枢](../prototype/index.html) · [交办](../prototype/index.html) | 新用户可交办、找业务或找衙门。切换页面和刷新保留草稿。普通任务可创建、模拟交付、验收并从版图找回同一县。 |
| [王朝总图](../prototype/index.html) · [学习省／模型研习府](../prototype/index.html) | 由总图进入行省、府州、县和案卷。地图和列表按同一份任务数据展示。支持搜索，输入不存在的案号会得到错误提示和搜索入口。 |
| [京城衙署](../prototype/index.html) · [门下省](../prototype/index.html) · [御前](../prototype/index.html) | 18 处可进入的场所包含御前、内阁、三省、六部、御史台、察院、台院、大理寺、翰林院、探查司、国史馆。桌面建筑和手机名录进入同一详情；每处显示职责、待办和对应入口。门下队列只显示本署经办，御前展示待用户批准。 |
| [正式案卷 YL-035](../prototype/index.html) | 内阁票拟 → 中书题本 → 门下复核或封驳 → 适用时由 用户 席位模拟朱批 → 尚书派办 → 责任部办理 → 验收和台院抽验。批准绑定当前案号、版本和范围。示例案卷展示人工点击后的状态推进。 |
| [察院登记](../prototype/index.html) · [大理寺核证](../prototype/index.html) · [台院抽验](../prototype/index.html) | 可登记示例疑点 JC-001 并在大理寺按同号回查；缺少独立核证身份时停在待核证。台院有交付抽验入口，监督案的真实整改和独立复验销案留待产品验收。 |
| [国史馆](../prototype/index.html) · [周报](../prototype/index.html) | 可查示例熟地的县志和原案。周报只演示在固定样例周手动补跑及回查；范围和统计口径以正式周报约定为准。 |

## 4. 下一轮设计怎么验

1. 先做可点的核心场景供 用户 评审。中枢从“我现在要办什么”出发，版图从“我的业务进展在哪”出发，衙门从“这件事归谁、进去能办什么”出发。展示一条普通任务和一条正式案卷，用同一内容比较视觉方向。先确认空间关系、信息层级和审美，再铺开所有衙署。
2. 让首次使用者在没有讲解的情况下完成交办、找到待自己批示的案卷、认出当前经手人、打开一个衙门待办、从版图查回成果。观察首次点击、误入、回退和卡住的位置，再确定页面结构。检验桌面、小屏、键盘与列表等价入口。
3. 重做 UI 时保住已有交互回归。草稿不丢、错案不串、官署待办归属准确、批示范围和身份可见、阻塞时有下一步、同一案卷可以跨中枢／衙门／版图回查。样式评审与真实模型、权限、持久化的验收分开，分别记录结果。
